# MyOwn Portal 1.1.0

Release for the InterSystems Programming Contest "AI Agents in Interoperability Workflows". 1.0.3 was a compact administration portal for InterSystems IRIS and IRIS for Health; 1.1.0 adds an AI agent that works inside an interoperability production. The agent decides and proposes; a person confirms every change with their own credentials.

## What changed since 1.0.3

### An AI agent inside an interoperability workflow

- New production `MyOwn.Production.Main`. Business Services turn health anomalies, failing tasks, serious log entries and role requests into events. Business Processes ask the `AgentGateway` operation for a decision, run the Gate and store the proposal. Every step leaves a message or an Event Log entry with the trace id.
- Two decision engines behind the gateway. The **AI Hub engine** (`%AI.Agent` with a read-only ToolSet, an allow-list authorization policy, an audit policy and its own deadline) runs on IRIS AI Hub builds. The **Rules engine** is always available. When AI Hub is missing, there is no key, the kill switch is on, the budget is spent or the provider fails, Rules decide, and the reason is recorded and shown (for example `Rules (provider_timeout)`).
- The agent's tools are read-only class queries (`GetTaskRuns`, `GetMetricHistory`), and the ToolSet excludes every tool whose name does not start with `Get`.

### Guardrails: the agent never writes

- **Validator.** The model output must be one JSON object that matches schema v1: strict types, allow-listed fields and actions, bounded text, targets taken only from the candidates the server supplied. 92 hostile model outputs are in the adversarial test corpus.
- **Gate.** Kill switch, read-only mode, prohibited targets (for example the `%All` role), high-risk decisions downgraded to escalation, one open proposal per target and action, budget and cooldown.
- **Human confirmation.** A state change exists only as a proposal that expires. Confirming it revalidates everything: state, expiry, separation of duties (a requester cannot confirm their own request), prohibited targets, the target fingerprint (`TARGET_CHANGED`) and the confirming user's live permission. The change is then executed with that user's credentials, read back and audited (`MyOwn/Agent/*`).
- Untrusted text (log lines, task errors, justifications) reaches the model only inside delimiters, sanitized.

### Replay mode

- `MYOWN_AI_MODE=replay` answers from real model decisions recorded earlier (Gemini `gemini-3.8-flash`), one fixture per scenario in `aihub/fixtures/`, each with its provider, model and recording date. It needs no key and no network, and the screen says "Replay of recorded real decisions". A scenario without a recording falls back to Rules (`replay_missing`); nothing is invented.

### Demo mode and the demo user

- `MYOWN_DEMO_MODE=1` makes the portal safe to expose. The `demo` account (role `MyOwnDemo`) can view the portal, run the scenarios and confirm or reject proposals; it has no IRIS administration privilege.
- Confirmations change only synthetic targets (demo tasks, users and roles) and end as `simulated`; IRIS itself is never changed. Routes that would change the real system are off for everyone. A reset task and a "Reset demo" button restore the synthetic state, and scenarios are rate-limited per client and session.
- The demo password is generated by `scripts/New-DemoPassword.ps1` into the git-ignored `.env` (`MYOWN_DEMO_USER_PASSWORD`) and never printed. Without it the demo account stays disabled.

### Custom inbound adapters

- `TaskWatcher` and `LogWatcher` use the portal's own adapters, `MyOwn.Production.Adapter.TaskHistoryInbound` and `LogEntriesInbound` (both `Ens.InboundAdapter`), with their settings in the production: `TaskNamespace`, `HistoryRows`, `FailureThreshold`, `MinSeverity`, `MaxEntries`.

### Packaging and installation

- **One IPM module**, `myown-portal`. The AI Hub engine is part of it and is compiled only where the `%AI` package exists; elsewhere the portal runs on Rules. The registry package contains no test classes.
- Installing into a namespace without interoperability enables it first (`MyOwn.Bootstrap`). The agent production is set to start automatically and starts once the install finishes. Uninstalling stops it and removes the web applications and classes; roles, resources and data are kept.
- **Docker** for IRIS AI Hub build 2026.3.0AI.154.0. The image build sets the production to start at boot, so a new installation has no error in its Event Log. An incomplete installation never starts. The ports are published on `127.0.0.1` only by default.
- `scripts/Test-All.ps1` runs every test suite, prints one table and exits with 1 when anything fails.

The portal itself (Overview with an Embedded Python health score and a Vector Search nearest-pattern match, Logs, users and roles through SysAdmin API v2, tasks, web applications, API explorer) is unchanged in purpose and still works without the agent.

## How to install

### Docker with IRIS AI Hub build 154 (recommended for the agent)

Load and tag the build 154 image once per machine, copy `.env.example` to `.env` (set your own `MYOWN_DEMO_PASSWORD`, and a key, or `MYOWN_AI_MODE=replay`), then:

```shell
docker compose -f compose.yaml -f compose.aihub.yaml up --build -d
```

Open `http://localhost:52774/myown/index.html`. The README has the full steps, the memory needed (tested with WSL limited to 8 GB on a 16 GB machine) and how to verify the installation.

### IPM

When 1.1.0 is published in the community registry, in the namespace where the portal should live:

```objectscript
zpm "install myown-portal"
```

Until then the registry has 1.0.3; to install 1.1.0 from a clone, `zpm "load /path/to/Portal-Iris"`.

## Known limitations

- Only the Gemini provider was used for real calls (`gemini-3.8-flash`, free tier). OpenAI, Anthropic and Bedrock go through the same `%AI.Provider` path but are untested.
- Gemini free-tier latency was 12 to 83 s per decision, against the portal's 20 s default deadline, so live decisions often fall back to Rules (`provider_timeout`). The provider also retries HTTP 429 and 503 on its own before reporting them. The online demo therefore uses replay mode.
- Replay fixtures S2 to S4, S8 and S9 come from earlier calls with equivalent, not identical, contexts (each fixture header says so); re-recording them stopped on provider 503 "high demand" answers.
- The IRIS edition of build 154 was not tested; only IRIS for Health.
- A viewer (`MyOwnViewer`) cannot file an access request: SysAdmin API v2 refuses it even its own account. The portal answers with a clear 403 and administrators file requests.
- The image build needs about 2.3 GB inside the Docker VM at its peak, and loading the image archive also needs memory; with other programs open, Windows can run low.
- The UI test suite needs Node.js; without it `Test-All.ps1` skips that suite.
- The default `_SYSTEM` password in `.env.example` is a well-known local convenience value. Change it before exposing the portal.
